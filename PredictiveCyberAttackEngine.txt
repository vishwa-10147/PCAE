1. Project summary (1-line)

Build an ML system that consumes historical attack/telemetry data + service/vulnerability data and outputs Attack Probability Scores per asset / network segment, with a dashboard that visualizes predicted hotspots and suggested mitigations.

2. Topics & concepts you’ll need to understand / cover

Network telemetry & logs — Netflow, firewall logs, web server logs, auth logs, IDS/IPS alerts.

Threat intelligence & IoCs — malicious IPs, domain lists, malware hashes.

Vulnerability data — CVE feed, host asset inventory, patch status.

Time-series forecasting & anomaly detection — sequence models, temporal features.

Supervised classification / ranking — probability of attack on an asset in a time window.

Feature engineering for cybersecurity — session counts, failed logins, port scan indicators.

Labeling & ground truth — mapping historical incidents to assets/time windows.

Model evaluation in imbalanced data — precision/recall, AUC-PR, time-to-detect metrics.

Deployment & visualization — streaming ingestion (optional), REST API, dashboard (React/Plotly/D3).

Security & privacy — handling sensitive logs, anonymization, safe demo practices.


3. High-level architecture

Data sources ? Ingestion layer (batch or streaming) ? Feature store / ETL ? Model training pipeline ? Inference service (REST) ? Dashboard + Alerts.

Optional: Threat intel microservice and vulnerability sync that enrich features.

4. Data sources (public & synthetic)

(You can use a mix of public datasets + synthetic data for assets you control.)

Public datasets (good for hackathon prototypes): CICIDS2017, CIC-IDS2018, UNSW-NB15, KDD Cup 99 (older), MAWILab, CTU-13 botnet dataset.

Threat Intel: open lists of malicious IPs/domains (for enrichment).

Asset inventory: CSV of hosts with OS, services, CVEs (can be synthetic).

Synthetic telemetry: generate flows/login attempts to simulate normal vs attack patterns (useable for demo if real logs unavailable).

5. What you will predict (problem statement formalized)

For each asset (or network segment) and a chosen prediction window (e.g., next 1 hour / next 24 hours), predict probability P(attack) that the asset will receive a malicious event. Output: asset_id, timestamp, attack_probability, top_contributing_features, recommended_action.

6. Labels (how to create ground truth)

Use IDS alerts, known incident timestamps, or attack rows from datasets.

Aggregate labels per asset/time window: if any malicious event occurred in that window ? label = 1, else 0.

Consider multi-label: attack type (recon, brute-force, data-exfil).

7. Feature ideas (per asset per time window)

Split into static and temporal features.

Static:

OS, open service ports, number of known CVEs, patch_age, asset_criticality.

Temporal (last N minutes/hours):

number_of_unique_src_ips, failed_logins_count, ssh_conn_count, http_4xx_count, http_5xx_count, avg_pkt_size, netflow_bytes_in/out, connection_entropy, new_ports_scanned, IDS_alert_count, ratio_failed_to_success_logins, domain_reputation_hits, blacklisted_ip_hits, previous_attack_count (moving window).

Derived:

trend_slope(feature) over last k windows, seasonality indicators (hour_of_day, day_of_week), anomaly-score from unsupervised model (e.g., IsolationForest).

8. Modeling approaches (progressive)

Start simple, then advance.

Phase A — baseline:

Logistic Regression / XGBoost / RandomForest on engineered features (easy + interpretable).

Phase B — temporal models:

LSTM / GRU or Temporal Convolutional Networks on sequences of per-window features.

Phase C — hybrid & graph:

Use Graph Neural Networks (assets as nodes, network adjacency) to capture lateral movement risk.

Combine sequence model outputs + GNN for final score.

Explainability:

SHAP values, or per-feature contributions for each prediction so dashboard can show "why".

9. Evaluation metrics

Precision / Recall / F1 (focus on high precision OR high recall depending on tolerance)

AUC-ROC and AUC-PR (imbalanced)

Time-to-detection improvement (how early you predicted before the detected incident)

Lead-time distribution (how many hours earlier the model raised a high probability than the actual attack)

Confusion matrix per asset type / attack type.

10. Threat model & ethical considerations

Don’t expose real credentials or PII in public demos.

Anonymize logs.

For demo data, prefer synthetic data or sanitized real logs.

Make clear predictions are probabilistic and require human analyst verification.

11. Tech stack (recommended)

Data ingestion/ETL: Python (pandas), Apache Kafka (optional streaming), Airflow (optional).

Feature store: PostgreSQL or Redis for fast features.

ML: Python, scikit-learn, XGBoost, PyTorch/TensorFlow for sequence models.

Explainability: SHAP.

Backend API: FastAPI or Flask (Python).

Dashboard: React + Plotly / Dash / Streamlit (fast prototype).

Containerization: Docker.

Optional: Elastic Stack (Elasticsearch + Kibana) for logs.

# sliding-window aggregation (pandas)
import pandas as pd
logs = pd.read_csv('netflow.csv')  # columns: ts, src_ip, dst_ip, src_port, dst_port, bytes, protocol, flag
logs['ts'] = pd.to_datetime(logs['ts'])
logs.set_index('ts', inplace=True)

# define window size
window = '1H'
agg = logs.groupby([pd.Grouper(freq=window), 'dst_ip']).agg({
    'src_ip': lambda s: s.nunique(),
    'bytes': 'sum',
    'dst_port': lambda s: s.nunique(),
    'flag': lambda s: (s=='SYN').sum(),
}).reset_index().rename(columns={'src_ip':'unique_src_ips', 'bytes':'total_bytes', 'dst_port':'unique_dst_ports'})

17. Possible extensions (competition differentiators)

Add graph propagation risk: if one asset is compromised, compute probability of lateral compromise.

Real-time streaming inference with Kafka + consumer.

Automated mitigation playbooks (e.g., block IPs temporarily).

Add uncertainty estimation (calibrate probabilities, provide confidence intervals).

18. Risks & mitigation

Imbalanced data ? use resampling, class weights, focal loss.

Label noise ? cross-check across multiple data sources or use weak-supervision to improve labels.

False positives ? tune for low FPs, provide analyst triage UI, and let threshold be configurable.
